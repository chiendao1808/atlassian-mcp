# Jira Tools

The Jira module registers these tools after valid static `JIRA_BASE_URL` configuration:

| Tool | Access | Notes |
|---|---|---|
| `jira_authenticate` | Sensitive session setup | Accepts username and password for this process only. Result `data.server` and `data.user` are redacted before return. Review MCP client logging/history policy before use. |
| `jira_get_issue` | Read-only | Reads one issue by `issueIdOrKey` and returns Jira's JSON under `data.issue`; optional `fields` and `expand` are comma-joined and passed through. |
| `jira_add_issue_comment` | Additive write | Adds a comment; optional visibility uses Jira native `role` or `group`. The server does not replay ambiguous POST failures. |
| `jira_update_issue_fields` | Write | Sends native Jira `fields` and/or `update` JSON; `returnFields` and `returnExpand` require `returnIssue=true`; read-back can return partial success on refresh failure. |
| `jira_transition_issue` | Write | Transitions by ID or exact name; duplicate names are rejected as ambiguous. `returnFields` and `returnExpand` require `returnIssue=true`. |
| `jira_create_issue` | Additive write | Creates one issue from native Jira `fields` (required) and optional `update` JSON; `data` is the redacted created object (`id`, `key`, `self`). No post-mutation read-back (there is no pre-existing issue to refresh). |
| `jira_bulk_create_issues` | Additive write | Creates multiple issues in one call from `issueUpdates` (required, non-empty list of `{fields, update?}`); `data` is the redacted upstream `{issues, errors}` body as-is. A non-empty `errors` array does **not** make the tool report failure -- callers must inspect `data.errors` themselves to see which rows failed. |
| `jira_delete_issue` | Destructive write | Permanently deletes one issue by `issueIdOrKey`; `deleteSubtasks` is sent only when explicitly set to `true`. Irreversible: no post-mutation read-back (the issue no longer exists). |
| `jira_assign_issue` | Destructive write | Assigns or unassigns an issue's assignee. `name` empty or omitted sends the literal body `{"name": ""}` to unassign (never a null body); a non-empty `name` assigns that user. Whether an empty-string body actually unassigns is Jira project/server config-dependent. Supports the same `returnIssue`/`returnFields`/`returnExpand` read-back triad as `jira_update_issue_fields`. |
| `jira_search_issues` | Read-only | Runs a JQL search (`jql` required) via Jira's POST search endpoint to avoid URL-length limits; optional `startAt`, `maxResults`, `fields`, `expand`, `validateQuery` are included in the request only when the caller sets them. `data` is the redacted `{startAt, maxResults, total, issues}` response. |
| `jira_list_issue_comments` | Read-only | Lists one issue's comments with optional `startAt`/`maxResults` pagination and comma-joined `expand`. `orderBy` is sent only when the caller sets it non-blank -- whether Jira 6.4.14 honors `orderBy` on this endpoint at all is itself patch-dependent, so it is never defaulted or guessed. `data` is the redacted `{startAt, maxResults, total, comments}` response. |
| `jira_update_issue_comment` | Write | Updates one comment's `body` (required) and optional `visibility` (native `role`/`group`, same validation as `jira_add_issue_comment`) by `issueIdOrKey`/`commentId`. `data.comment` always carries the redacted updated comment; supports the same `returnIssue`/`returnFields`/`returnExpand` read-back triad as `jira_update_issue_fields`, adding `data.issue` alongside `data.comment` on a successful refresh. `expand` is accepted on input for schema parity with Jira's optional query on this endpoint, but is not currently forwarded to Jira -- the shared PUT client helper has no query-parameter support (a future `PutJSONQuery`, mirroring the existing `PostJSONQuery`, would be needed to add it). |
| `jira_delete_issue_comment` | Destructive write | Permanently deletes one comment by `issueIdOrKey`/`commentId` (204, no body). Unlike `jira_delete_issue`, the parent issue still exists afterward, so it supports the same `returnIssue`/`returnFields`/`returnExpand` read-back triad as `jira_assign_issue`. |
| `jira_list_issue_transitions` | Read-only | Lists an issue's available workflow transitions; `transitionId` optionally filters to one. `expand` defaults to `transitions.fields` (the spec's own recommendation for seeing required transition-screen fields) when the caller omits it; a caller-supplied `expand` replaces that default outright rather than being merged with it. `data` is the redacted `{transitions}` response. |
| `jira_add_issue_attachment` | Additive write | Uploads one file to an issue by `issueIdOrKey`, `filename` (required), and `contentBase64` (required) -- content must be base64-encoded since MCP tool inputs are JSON-only and carry no raw file handle; an invalid `contentBase64` value fails validation before any network call. Jira 6.4.14 responds with **HTTP 200 (not 201)** and a **JSON array** of attachment objects, which is wrapped and redacted as `data.attachments`. Supports the same `returnIssue`/`returnFields`/`returnExpand` read-back triad as `jira_update_issue_fields`. |
| `jira_delete_issue_attachment` | Destructive write | Permanently deletes one attachment by `attachmentId` (required) only -- this endpoint's REST path is `/attachment/{id}`, with **no issue key** anywhere in the path or this tool's input. No post-mutation read-back triad (there is no issue key to anchor a refresh). Irreversible. |
| `jira_list_issue_worklogs` | Read-only | Lists one issue's worklog entries by `issueIdOrKey`. `data` is the redacted `{startAt, maxResults, total, worklogs}` response. |
| `jira_add_issue_worklog` | Additive write | Records a worklog entry on `issueIdOrKey` with `timeSpentSeconds` (required, must be `> 0`); optional `comment` and `started` (a Jira-format datetime string, passed through as-is). Optional `adjustEstimate` must be exactly one of `new`, `leave`, `manual`, `auto`; when set, `adjustEstimate` plus optional `newEstimate`/`reduceBy` are sent as **query parameters**, while `comment`/`started`/`timeSpentSeconds` are sent in the **JSON body** -- mirroring Jira's own request shape for this endpoint. `data.worklog` carries the redacted created worklog object (HTTP 201). Supports the same `returnIssue`/`returnFields`/`returnExpand` read-back triad as `jira_update_issue_fields`. |
| `jira_get_issue_watchers` | Read-only | Lists one issue's watchers by `issueIdOrKey`. `data` is the redacted `{isWatching, watchCount, watchers}` response. |
| `jira_add_issue_watcher` | Additive write | Adds `username` (required) as a watcher on `issueIdOrKey`. The request body is the **bare JSON string** `username` itself (e.g. `"bob"`), not an object -- this is Jira's own wire shape for this endpoint, not a bug. Supports the same `returnIssue`/`returnFields`/`returnExpand` read-back triad as `jira_update_issue_fields`. |
| `jira_remove_issue_watcher` | Destructive write | Removes `username` (required) as a watcher from `issueIdOrKey`. Unlike `jira_add_issue_watcher`, `username` travels on the **query string** here, with no request body at all. Supports the same `returnIssue`/`returnFields`/`returnExpand` read-back triad as `jira_assign_issue`. Irreversible in the sense that the caller must re-add the watcher explicitly to undo it. |
| `jira_vote_issue` | Additive write | Adds the authenticated user's vote to `issueIdOrKey` via a bodyless POST (204, no response body). Supports the same `returnIssue`/`returnFields`/`returnExpand` read-back triad as `jira_update_issue_fields`. |
| `jira_unvote_issue` | Destructive write | Removes the authenticated user's vote from `issueIdOrKey` via a DELETE with no query parameters and no body (204). Supports the same `returnIssue`/`returnFields`/`returnExpand` read-back triad as `jira_assign_issue`. |
| `jira_create_issue_link` | Additive write | Creates a native Jira issue link from `type`, `inwardIssue`, and `outwardIssue` (all required native Jira JSON objects, e.g. `type: {"name":"Blocks"}`, `inwardIssue: {"key":"PROJ-123"}`) plus optional `comment`. The REST path is `/issueLink` at the API root -- **not** nested under `/issue/...` -- so no `issueIdOrKey` path validation applies to this tool. Jira typically returns 201 with no response body, so success is reported as `data.mutationApplied: true`. No post-mutation read-back triad: two issues are involved and there is no single unambiguous anchor to refresh. |

All tool results use the shared envelope: `success`, `service`, `tool`, `data`, `error`, and optional `meta`.
